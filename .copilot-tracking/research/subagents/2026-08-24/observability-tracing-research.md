# Research: Agent Observability, Tracing Standards, and Telemetry Schemas for Autonomous AI Agents

## Research Topics/Questions

1. OpenTelemetry GenAI semantic conventions: standardized spans/attributes for LLM calls, agent steps, tool invocations (`gen_ai.*`).
2. Agent/LLM observability platforms (LangSmith, Langfuse, Arize Phoenix, Helicone, W&B Weave, Braintrust, OpenLLMetry/Traceloop, AgentOps): what they capture, trajectory structuring, open-source vs commercial/self-hostable.
3. Common schema for "trajectory"/"run" modeling: root trace + nested spans; hierarchical/multi-agent trace support.
4. Conventions for capturing recovery/retry events, human-in-the-loop escalations, policy violations in agent traces.
5. Storage/query technologies paired with these systems (ClickHouse, Postgres+JSONB, vector DBs, time-series DBs).

## Findings

### 1. OpenTelemetry GenAI Semantic Conventions

**Important note on location**: The canonical spec has *moved* out of the main `open-telemetry/semantic-conventions` repo. The old docs page (opentelemetry.io/docs/specs/semconv/gen-ai/) now just redirects. The live spec lives in a dedicated repo:
- Repo: https://github.com/open-telemetry/semantic-conventions-genai
- Spans doc: https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-spans.md
- Agent/framework spans doc: https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md
- Events doc: https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-events.md
- General "Recording errors" doc (still in main semconv repo): https://github.com/open-telemetry/semantic-conventions/blob/main/docs/general/recording-errors.md

All GenAI conventions are currently at **"Development"** stability status (not yet Stable), so attribute names/shapes can still change. `error.type` and `server.address`/`server.port` are the only Stable attributes reused from core semconv.

**Core attribute namespace**: everything is prefixed `gen_ai.*`, following the general OTel semconv pattern of `{signal}.{attribute}`.

**`gen_ai.operation.name`** is the key discriminator for span/event type. Well-known values (all "Development" stability):
`chat`, `generate_content`, `text_completion`, `embeddings`, `retrieval`, `execute_tool`, `create_agent`, `invoke_agent`, `invoke_workflow`, `plan`, `create_memory`, `create_memory_store`, `delete_memory`, `delete_memory_store`, `search_memory`, `update_memory`, `upsert_memory`, `fetch_response`.

**`gen_ai.provider.name`** identifies the backing model/service (`openai`, `anthropic`, `aws.bedrock`, `azure.ai.openai`, `azure.ai.inference`, `cohere`, `deepseek`, `gcp.gemini`, `gcp.gen_ai`, `gcp.vertex_ai`, `groq`, `ibm.watsonx.ai`, `mistral_ai`, `moonshot_ai`, `perplexity`, `x_ai`).

**Span types defined (gen-ai-spans.md, "client" spans — the LLM-call level)**:
- **Inference** — the core LLM call span (`gen_ai.operation.name` = chat/generate_content/text_completion). Span name pattern: `{operation.name} {request.model}`. Key attributes: `gen_ai.request.model`, `gen_ai.request.temperature/top_p/top_k/max_tokens/stop_sequences/seed/frequency_penalty/presence_penalty`, `gen_ai.response.model/id/finish_reasons`, extensive `gen_ai.usage.*` token-count breakdowns (input/output/cache_read/cache_write/reasoning/audio/image/text sub-splits), `gen_ai.conversation.id` (session/thread correlation — explicitly must NOT be a synthetic UUID/trace-id fallback), `gen_ai.conversation.compacted` (flags context-compaction), `gen_ai.request.previous_response.id` (chains to prior turn, maps to OpenAI Responses API's `previous_response_id`).
  - Content capture (`gen_ai.input.messages`, `gen_ai.output.messages`, `gen_ai.system_instructions`, `gen_ai.tool.definitions`) is **Opt-In only** — off by default due to PII/sensitive-data risk, must follow a public JSON Schema (linked from spec), and instrumentations are told to prefer uploading large/sensitive payloads to external storage and referencing them from the span rather than inlining, in production.
- **Embeddings** — `gen_ai.operation.name=embeddings`, dimension count, encoding formats.
- **Retrievals** — `gen_ai.operation.name=retrieval`; `gen_ai.data_source.id`, `gen_ai.retrieval.top_k`, opt-in `gen_ai.retrieval.documents` (each doc: `id`, `score`), opt-in query text. This is the RAG-retrieval-step convention.
- **Fetch response** — async/background response polling pattern (OpenAI Responses API style), with `gen_ai.response.status` enum (`queued|in_progress|incomplete|completed|failed|cancelled`).
- **Memory** — CRUD-style spans for agent memory stores (`create_memory_store`, `search_memory`, `create_memory`, `update_memory`, `upsert_memory`, `delete_memory`, `delete_memory_store`), with `gen_ai.memory.store.id`, `gen_ai.memory.record.id/count`, opt-in `gen_ai.memory.records`.
- **Execute tool span** — `gen_ai.operation.name=execute_tool`; span name `execute_tool {gen_ai.tool.name}`; kind `INTERNAL`. Attributes: `gen_ai.tool.name`, `gen_ai.tool.call.id`, `gen_ai.tool.description`, `gen_ai.tool.type` (enum: `function` = client-side execution, `extension` = agent-side direct API call, `datastore` = RAG/knowledge access), opt-in `gen_ai.tool.call.arguments` / `gen_ai.tool.call.result`. `gen_ai.agent.name` may be attached when the executing agent is known. Note: MCP tool calls may instead be captured by a separate MCP-specific semconv doc (`gen-ai/mcp.md`) if using MCP instrumentation.

**Agent/framework-level spans (gen-ai-agent-spans.md — this is the direct answer to "agent steps")**:
- **Create agent span** (`create_agent`) — agent provisioning/registration, mainly for *remote/hosted* agent services (e.g., an AWS Bedrock agent or OpenAI Assistant being created). `gen_ai.agent.id/name/version/description`.
- **Invoke agent (client) span** (`invoke_agent`, kind=CLIENT) — for calling a *remote* hosted agent (OpenAI Assistants API, AWS Bedrock Agents).
- **Invoke agent (internal) span** (`invoke_agent`, kind=INTERNAL) — for *in-process* agent frameworks (LangChain agents, CrewAI). This is likely the most relevant span type for ARISE-X's in-process agent execution model.
- **Invoke workflow span** (`invoke_workflow`) — represents a *multi-agent orchestration/graph* execution (LangGraph `Graph.invoke()`, CrewAI `Crew.kickoff()`, ADK `Runner.run()` with multi-agent, Microsoft Agent Framework `Workflow.run()`, OpenAI Agents SDK `Runner.run()` with handoffs/sub-agents). Explicitly should **only** be reported for user-facing orchestration entry points, not internal implementation details — this is the direct evidence for how OTel models **multi-agent/hierarchical traces**: `invoke_workflow` (root) → `invoke_agent` (per sub-agent) → `plan`/`execute_tool`/inference spans (per step), and workflows can nest (sub-graph as a node of another graph). `gen_ai.workflow.name` is required to be a low-cardinality, application-defined name (not a class name like "StateGraph").
- **Plan span** (`plan`) — a distinct, optional span type for agent planning/task-decomposition phases; the LLM call that generates the plan is a *child* of the plan span, and resulting tool/task spans are typically *siblings* under the same parent `invoke_agent` span. This is the closest thing OTel has to standardizing a "reasoning/planning step" in an agent trajectory.

**Span kind conventions**: CLIENT for calls that cross a process/network boundary (inference, embeddings, retrieval, remote agent invocation); INTERNAL for in-process operations (tool execution, internal agent invocation, workflow orchestration, planning).

**Events**:
- `gen_ai.client.inference.operation.details` — an alternative/complementary way (via OTel Logs/Events, not spans) to record full input/output/parameters independently of the trace — same opt-in content-capture rules apply.
- `gen_ai.evaluation.result` — **directly relevant to ARISE-X's drift/reliability scoring plane**. Standardized event for recording an evaluation/score against a GenAI operation: `gen_ai.evaluation.name` (metric name, e.g. "Relevance", "IntentResolution"), `gen_ai.evaluation.score.value` (double) and/or `.score.label` (human-readable, e.g. "relevant"/"pass"/"fail"), `gen_ai.evaluation.explanation` (free text), `error.type` if the evaluator itself errored, and `gen_ai.response.id` to correlate back to the scored response when a direct span-parent link isn't available.

**Retry/error handling (from the general `recording-errors.md` doc, since GenAI spans inherit it)**: There is **no dedicated "retry event" or "recovery event" attribute** in the GenAI conventions. Instead, the general OTel philosophy applies:
- A logical operation span **should cover the full duration including any automatic retries** — i.e., retries are *not* separately surfaced as sibling spans/events by default; the outer span just runs longer.
- "Errors that were retried or handled (allowing an operation to complete gracefully) SHOULD NOT be recorded on spans or metrics that describe this operation" — i.e., transient/handled errors should not flip span status to Error or set `error.type`. Only errors that propagate out of the operation should mark it failed.
- Exceptions should be recorded once (as an exception log/event) at the point they are *not* handled — recording the same exception at multiple layers is discouraged.
- This means: if ARISE-X wants explicit retry-attempt visibility (e.g., "LLM call retried 3x due to rate limit before success"), that requires a **custom, non-standard attribute/event** (e.g., `gen_ai.request.retry_count`, or child spans per attempt) — there is no OTel-blessed convention for this yet.

**No standard convention exists for**: human-in-the-loop escalation events, or policy/guardrail-violation events, as first-class GenAI semconv attributes. (Confirmed via targeted search of the semantic-conventions-genai repo — no hits for "human-in-the-loop"/"interrupt"/"escalation"/"guardrail".) These are handled today at the *application framework* level (see LangGraph findings below) or via generic OTel span/log attributes chosen ad hoc by each vendor. The closest standardized hook is the `gen_ai.evaluation.result` event, which could be repurposed to record a guardrail/policy check outcome (e.g., `gen_ai.evaluation.name="policy_violation"`, `score.label="blocked"`).

### 3. Common Trajectory/Run Schema Across Platforms

Despite different terminology, every platform reviewed converges on essentially the same **two/three-level hierarchy**, which maps directly onto OTel's trace/span model:

1. **Leaf/step unit** = OTel span equivalent: LangSmith `Run`, Langfuse `Observation`, Weave `Call`, Braintrust `Span` (typed), AgentOps `Operation`/`Task` span, Phoenix/OpenInference/OpenLLMetry = literal OTel span.
2. **Single logical execution** = OTel trace equivalent: LangSmith `Trace`, Langfuse `Trace`, Weave `Trace`, Braintrust `Trace`, AgentOps `Session`/`Trace` — a tree of step-units sharing one root/trace ID, capturing the full nested execution (LLM calls, tool calls, retrieval, sub-agent calls) of one request/run.
3. **Multi-turn / multi-trace session** = a grouping layer above traces: LangSmith `Thread`, Langfuse `Session`, Weave `Thread`, Phoenix `Session` — all represent "a sequence of traces belonging to one conversation/user session," typically linked via a shared `thread_id`/`session_id` metadata key rather than a first-class parent-span relationship.

**Hierarchical / multi-agent trace support**: Confirmed as a first-class, explicitly-designed concept in the **OpenTelemetry GenAI Agent semconv** via the `invoke_workflow` → `invoke_agent` → (`plan` | `execute_tool` | inference) span nesting pattern, with explicit multi-agent/orchestrator framework examples cited (LangGraph, CrewAI, Google ADK, Microsoft Agent Framework, OpenAI Agents SDK handoffs). Vendor platforms don't need their own special-case for this — because they ingest/model plain nested spans, a multi-agent trace is "just" a deeper span tree (sub-agent invocations nest under a parent agent/workflow span) and every platform in the table above renders arbitrarily deep nesting natively.

**LangSmith's `Trajectory` concept is the most distinct schema idea found**: rather than one more hierarchy variant, it is a *view* — a flattened, deduplicated, chronologically-ordered list of only the human/AI/tool *messages* exchanged in a thread, with the run-tree nesting stripped out. This is presented as complementary to (not a replacement for) the full nested trace, specifically for the use case of "read what was exchanged, without execution detail." This is directly relevant to ARISE-X's stated need to capture "full agent trajectories" — it suggests ARISE-X's Telemetry Plane may want to support **two projections of the same underlying span data**: (a) the full nested trace tree for debugging/root-cause, and (b) a flattened trajectory/message-sequence view for trajectory-level drift/behavior analysis.

### 4. Recovery/Retry, Human-in-the-Loop, and Policy-Violation Conventions

**No unified industry standard exists** for any of these three concerns as of this research. Findings per concern:

- **Retry/recovery events**: OpenTelemetry's general guidance (`recording-errors.md`) is that a *retried-and-recovered* operation should just be one longer-duration span with **no error status** — retries are invisible by default unless a vendor adds custom attributes. No platform reviewed publishes a standardized "retry attempt" span/attribute; this would be a custom ARISE-X extension (e.g., a `retry_count`/`recovery_action` attribute, or explicit sibling spans per attempt tagged with an outcome).
- **Human-in-the-loop (HITL) escalation**: The most concrete, production-grade pattern found is **LangGraph's `interrupt()` mechanism** (https://docs.langchain.com/oss/python/langgraph/human-in-the-loop): a node calls `interrupt(payload)`, which (a) raises a special exception that suspends the graph, (b) **persists full graph state via a checkpointer** keyed by `thread_id`, (c) surfaces the interrupt payload to the caller (`stream.interrupts` / `result["__interrupt__"]`), and (d) resumes via `Command(resume=<human response>)`, replaying the node from its start. This is a **state-machine/checkpoint pattern**, not a distinct trace-signal convention — from a telemetry standpoint, an ARISE-X equivalent would need to record: the interrupt payload/reason, the pending duration, the resuming actor (human user id), and the resume value, likely as a dedicated span (e.g., `gen_ai.operation.name` custom value like `human_approval`) bracketing the pause. LangSmith's "feedback" (tag+score bound to a run id) and annotation queues are the closest thing to a standardized *post-hoc* human-review signal, but that's evaluation, not blocking-escalation.
- **Policy violations / guardrails**: No dedicated OTel GenAI event type exists (`gen_ai.evaluation.result` is the nearest reusable primitive — it's generic enough to encode a guardrail check as a named "evaluation" with a `blocked`/`pass`/`fail` label and explanation). AgentOps ships a concrete but narrow feature here ("Honeypot and prompt injection detection," powered by a third-party "PromptArmor" integration) but treats broader safety/anomaly detection (infinite loops, faulty reasoning) as unshipped roadmap items, confirming this is still an open problem industry-wide, not a solved convention.
- **Practical implication for ARISE-X**: Since no standard exists, ARISE-X's Telemetry Plane should **define its own first-class event/attribute vocabulary** for these three concerns (e.g., `arise.recovery.*`, `arise.hitl.*`, `arise.policy.*` namespaces) while still emitting them as standard OTel spans/events (span kind `INTERNAL`, custom `gen_ai.operation.name`-style discriminator) so they remain interoperable with OTel collectors/backends. This is consistent with how the GenAI semconv itself evolved — provider- and framework-specific extensions are expected and namespaced (e.g., `aws.bedrock.*`, `openai.*`) alongside the core `gen_ai.*` set.

### 5. Storage/Query Technologies

Only Langfuse's architecture was directly documented in this pass (it is the only fully-OSS, self-hostable platform with a published reference architecture); the pattern is nonetheless broadly representative of how production LLM-observability backends are built:

**Langfuse self-hosted architecture** (https://langfuse.com/self-hosting, https://langfuse.com/self-hosting/infrastructure/clickhouse):
- **Postgres** — OLTP store for transactional/control-plane data (projects, users, API keys, prompts, config).
- **ClickHouse** — the OLAP store of record for **traces, observations, and scores** — i.e., the actual telemetry/trace data lives in ClickHouse, not Postgres, specifically because Langfuse needs "high write throughput and fast analytical queries" over large trace volumes. ClickHouse is a **hard requirement**, not optional, for self-hosting Langfuse (per their FAQ: "There is no alternative OLAP database supported at this time").
- **Redis/Valkey** — cache + queue (API-key cache, prompt cache, and the ingestion queue: incoming events are written to S3 first, referenced via a Redis queue entry, then asynchronously processed into ClickHouse by a worker — this decouples ingestion-request latency from database write latency and provides durability if ClickHouse is temporarily down).
- **S3/Blob storage** — durable raw-event landing zone (every incoming trace event is persisted here before processing, for recoverability) plus storage for large multi-modal attachments (images/video/files), which are uploaded directly from client SDKs rather than inlined in trace payloads.
- Both Postgres and ClickHouse must run in **UTC** (hard requirement, not just best practice).
- Officially-supported deployment targets: Docker Compose (dev/low-scale), Kubernetes Helm chart, and Terraform modules for AWS/Azure/GCP (production-scale).

**General pattern this confirms for ARISE-X's design** (consistent with widely-known industry practice for trace/observability backends, e.g., Jaeger/Tempo-style systems and other GenAI tools):
- **OLTP DB (Postgres, often with JSONB columns)** for control-plane/metadata entities (agents, configs, users, prompt/version records) where relational integrity and flexible ad hoc JSON fields both matter.
- **Columnar/OLAP store (ClickHouse is the dominant choice in this space)** for the actual high-volume trace/span/observation/event data, optimized for time+entity-filtered analytical queries (e.g., "all failed tool calls for agent X in the last 24h") rather than point lookups.
- **Object storage (S3-compatible)** as the durability/landing layer for raw ingested events and for large/binary payloads (multi-modal content, big tool outputs) that shouldn't live in the hot-path database.
- **In-memory cache/queue (Redis)** to decouple ingestion request latency from downstream write/processing latency and to cache frequently-read, slowly-changing data (API keys, prompt templates).
- **Vector databases** were not found to be used by any of these platforms for the *trace storage* itself; where relevant (RAG retrieval spans), vector DBs are the *instrumented target* (Pinecone/Qdrant/Weaviate/Chroma/Milvus/LanceDB, per OpenLLMetry's supported-integrations list), not the telemetry backend. If ARISE-X wants embedding-based analysis *of* trajectories (e.g., clustering similar failure trajectories), that would be a separate, additional vector-store use case layered on top of the OLAP trace store, not a substitute for it.
- No platform reviewed uses a dedicated time-series DB (e.g., Prometheus/InfluxDB) for trace *storage* — those are typically reserved for aggregate metrics (latency percentiles, cost-over-time), which ClickHouse's OLAP query engine can also serve directly from the raw trace data via materialized views/aggregations.
